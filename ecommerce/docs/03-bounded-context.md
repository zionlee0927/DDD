# 03. Bounded Context 경계

> "Bounded Context는 특정 모델이 정의되고 적용되는 경계를 명시적으로 설정한다." — Eric Evans

---

## 식별 과정

### 입력

- 0단계 서브도메인 목록
- 1단계 용어집 (같은 용어가 다른 의미로 쓰이는지)
- 2단계 이벤트 (어떤 이벤트들이 함께 발생하는지)

### 경계를 나타내는 6가지 신호

| 신호            | 질문                          | 분리 시그널                    |
|---------------|-------------------------------|------------------------------|
| 언어의 변화      | 같은 용어가 다른 의미로 쓰이는가?    | "링크"가 프로필 URL vs 추적 수단   |
| 팀/조직 경계     | 다른 팀이 담당할 수 있는가?        | 정산팀 vs 주문팀                |
| 변경 주기       | 변경 빈도가 다른가?              | 프로모션(주 단위) vs 결제(분기)    |
| 비즈니스 역량    | 독립적으로 가치를 제공하는가?       | "주문을 받을 수 있다"            |
| 데이터 소유권    | Source of Truth가 어디인가?     | 클릭 데이터 → Tracking BC       |
| 트랜잭션 경계    | 강한 일관성이 필요한 범위는?        | 재고 선점은 주문과 별도 트랜잭션     |

### 합칠지 분리할지 판단

| 질문                        | 합침   | 분리   |
|---------------------------|------|------|
| 같은 유비쿼터스 언어를 쓰는가?     | ✓    | ✗    |
| 항상 함께 변경되는가?            | ✓    | ✗    |
| 같은 팀이 소유하는가?            | ✓    | ✗    |
| 하나 없이 다른 하나가 의미 없는가?  | ✓    | ✗    |
| 변경 주기가 다른가?             | ✗    | ✓    |
| 기술 요구사항이 다른가?           | ✗    | ✓    |
| 독립적으로 배포/확장 가능해야 하는가? | ✗    | ✓    |

## BC 식별 결과

| Bounded Context | 포함 서브도메인         | 유형         | 분리 이유                            |
|-----------------|------------------|------------|----------------------------------|
| **Partner**     | 파트너 관리           | Core       | 독립적 생명주기. 파트너 등록/티어는 주문과 무관하게 변경 |
| **Tracking**    | 귀속 (Attribution) | Core       | 클릭 기록, 귀속 기간 관리. 실시간 이벤트 스트림 성격  |
| **Commission**  | 커미션 정산           | Core       | 완전히 다른 생명주기 (월 단위). 금융 정확성 별도 관리 |
| **Order**       | 주문               | Supporting | 주문 상태 관리. 독립 트랜잭션                |
| **Cart**        | 장바구니             | Supporting | 주문과 생명주기 다름 (오래 유지 vs 확정/취소)     |
| **Catalog**     | 상품 카탈로그          | Supporting | 상품 정보는 여러 BC가 참조. 데이터 소유권 명확     |
| **Inventory**   | 재고               | Supporting | 동시성 제어 단위. 주문과 별도 트랜잭션           |
| **Shipping**    | 배송               | Supporting | 외부 물류 연동. 주문 확정 후 독립 진행          |
| **Promotion**   | 프로모션             | Supporting | 할인 규칙 독립 변경 (주 단위). 주문과 변경 주기 다름 |
| **Payment**     | 결제               | Generic    | 외부 PG 연동. 표준적 솔루션                |

---

## 분리 근거

### 왜 Order와 Cart를 분리?
- 생명주기: 장바구니는 며칠~몇 주 유지, 주문은 생성 후 확정/취소
- 변경 주기: 장바구니 로직은 안정적, 주문 정책은 자주 변경

### 왜 Order와 Payment를 분리?
- 결제 실패해도 주문은 존재 (재시도 가능)
- PG 콜백은 Payment만 변경, Order까지 잠기면 성능 문제

### 왜 Tracking과 Commission을 분리?
- Tracking: 실시간 클릭 기록 (고빈도, 단순)
- Commission: 월 단위 정산 (저빈도, 금융 정확성)
- 변경 주기와 정확성 요구사항이 완전히 다름

### 왜 Partner와 Tracking을 분리?
- Partner: 파트너 프로필, 티어 관리 (CRUD 성격)
- Tracking: 클릭 이벤트 스트림, 귀속 판정 로직 (이벤트 처리 성격)
- 언어가 다름: Partner에서 "링크"는 프로필, Tracking에서 "링크"는 추적 수단

### 왜 Inventory를 Order에서 분리?
- 동시성: 재고는 여러 주문이 동시에 접근하는 공유 자원
- 트랜잭션: 재고 선점은 주문 트랜잭션과 별도로 관리해야 성능 확보

## Context Map

```
┌──────────┐         ┌──────────┐         ┌──────────┐
│ Partner  │────────→│ Tracking │────────→│Commission│
│  (Core)  │  링크    │  (Core)  │  귀속    │  (Core)  │
└──────────┘  발급    └──────────┘  데이터  └──────────┘
                          ↑                      ↑
                          │ 추적코드               │ 주문 확정/취소
                          │                      │
┌──────────┐         ┌──────────┐         ┌──────────┐
│ Catalog  │────────→│  Order   │────────→│ Payment  │
│(Support) │  상품    │(Support) │  결제    │(Generic) │
└──────────┘  정보    └──────────┘  요청    └──────────┘
     │                    │ │
     │                    │ │
     ▼                    ▼ ▼
┌──────────┐    ┌──────────┐ ┌──────────┐
│   Cart   │    │Inventory │ │ Shipping │
│(Support) │    │(Support) │ │(Support) │
└──────────┘    └──────────┘ └──────────┘

┌──────────┐
│Promotion │◄─── Order (주문 시 할인 조회)
│(Support) │
└──────────┘
```

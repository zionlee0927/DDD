# 이커머스 DDD 설계 문서

## 설계 순서

```
0. 서브도메인 분석 (문제 공간)
1. 유비쿼터스 언어 / 용어집
2. Event Storming (이벤트 → 커맨드 → 정책 → Aggregate)

6. Aggregate 설계

```

## 0단계: 서브도메인 분석 (문제 공간)

> "서브도메인은 발견하는 것이고, Bounded Context는 설계하는 것이다." — Nick Tune

### 도메인 정의

**도메인:** 인플루언서 중심 쇼핑몰

자사 상품을 직접 판매하되, 인플루언서(파트너)의 추천이 핵심 유입 채널인 쇼핑몰.
인플루언서가 추적 링크로 상품을 추천하고, 해당 링크를 통한 구매 발생 시 커미션을 정산받는다.

```
인플루언서 → 추적 링크로 상품 추천
소비자 → 추적 링크 클릭 → 우리 쇼핑몰에서 직접 구매
우리 → 인플루언서에게 커미션 정산
```

### 서브도메인 식별

| 서브도메인            | 유형         | 설명                                  |
|------------------|------------|-------------------------------------|
| 파트너(인플루언서) 관리    | **Core**   | 파트너 유치/등록, 티어 관리, 추적 링크 발급. 생태계의 핵심 |
| 귀속 (Attribution) | **Core**   | 추적 링크 → 주문 귀속 판정. 누가 추천했는지 추적/분석    |
| 커미션 정산           | **Core**   | 귀속된 주문 기반 커미션 계산, 정산 주기, 지급         |
| 주문               | Supporting | 주문 생성, 상태 관리, 취소/환불                 |
| 상품 카탈로그          | Supporting | 상품 정보, 카테고리, 검색                     |
| 장바구니             | Supporting | 구매 의사 임시 저장, 상품 선택                  |
| 재고               | Supporting | 수량 관리, 차감/복원                        |
| 배송               | Supporting | 배송 상태 추적, 외부 물류 연동                  |
| 프로모션             | Supporting | 할인 규칙, 쿠폰 발급/사용, 캠페인                |
| 결제               | Generic    | 외부 PG 연동, 결제 승인/취소                  |
| 회원               | Generic    | 가입, 인증, 프로필                         |
| 알림               | Generic    | 주문/배송/정산 알림                         |

### Core Domain 검증 (Distillation)

**파트너 관리가 Core인 이유:**

| 질문                   | 답                          |
|----------------------|----------------------------|
| 이 기능 없으면 비즈니스 존재 가능? | No — 인플루언서 없으면 그냥 평범한 쇼핑몰  |
| 경쟁사도 똑같이?            | No — 파트너 유치 전략, 티어 정책이 차별화 |
| 외부 솔루션 대체 가능?        | No — 우리 생태계에 맞는 파트너 관리 필요  |
| 혁신이 가치 창출?           | Yes — 좋은 인플루언서 확보 = 매출 성장  |

**귀속(Attribution)이 Core인 이유:**

| 질문                   | 답                                  |
|----------------------|------------------------------------|
| 이 기능 없으면 비즈니스 존재 가능? | No — 누가 추천했는지 모르면 커미션 지급 불가        |
| 경쟁사도 똑같이?            | No — 귀속 로직(쿠키 기간, 라스트클릭/멀티터치)이 차별화 |
| 외부 솔루션 대체 가능?        | No — 우리 주문 구조와 밀접하게 연결             |
| 혁신이 가치 창출?           | Yes — 정확한 귀속 = 파트너 신뢰 = 생태계 성장     |

**커미션 정산이 Core인 이유:**

| 질문                   | 답                                   |
|----------------------|-------------------------------------|
| 이 기능 없으면 비즈니스 존재 가능? | No — 파트너에게 돈을 못 주면 생태계 붕괴           |
| 경쟁사도 똑같이?            | No — 정산 주기, 커미션 규칙, 투명성이 파트너 유치 차별화 |
| 외부 솔루션 대체 가능?        | No — 귀속 데이터 기반 정산은 직접 구현 필수         |
| 혁신이 가치 창출?           | Yes — 빠른 정산, 실시간 리포트가 파트너 만족도에 직결   |

### Domain Vision Statement

> "우리의 핵심 경쟁력은 인플루언서 생태계다. 파트너가 쉽게 상품을 추천하고, 추천을 통한 구매가 정확히 추적되며, 투명하고 빠르게 커미션을 정산받는 경험을 제공한다. 이를 통해 더 많은 인플루언서가 유입되고, 더 많은 소비자가 신뢰할 수 있는 추천을 통해 구매하는 선순환을 만든다."

### Phase 1 범위

```
포함: 파트너, 귀속, 커미션 정산, 상품, 장바구니, 주문, 결제, 재고, 배송, 프로모션
제외: 회원(Spring Security로 최소 구현), 알림(나중에 추가)
```

10개 서브도메인으로 다양한 Context Mapping 패턴을 경험한다:

| 관계              | 패턴                | 학습 포인트              |
|-----------------|-------------------|---------------------|
| 파트너 → 귀속 → 정산   | Events 체인         | 이벤트 기반 연쇄 처리        |
| 주문 → 귀속         | Events            | 주문 확정 시 귀속 판정       |
| 정산 ← 귀속         | Events            | 완전히 다른 생명주기, 비동기 분리 |
| 상품 → 장바구니/주문    | OHS               | 여러 소비자에게 표준 API 제공  |
| 주문 → 프로모션       | C-S               | 할인 조회 (동기)          |
| 파트너 → 추적        | C-S               | 링크 발급 시 파트너 정보 조회   |
| 주문 → 재고         | C-S               | 재고 선점 (동기)          |
| 주문 ↔ 결제         | Partnership       | 결제 요청/완료 (양방향 비동기)  |
| 주문 → 배송         | Events            | 주문 확정 → 배송 시작       |
| 결제 → PG사        | ACL               | 외부 시스템 격리           |
| 배송 → 외부 물류      | ACL               | 외부 시스템 격리           |

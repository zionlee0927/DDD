# DDD 이론 04: Bounded Context 심화

> "Bounded Context는 특정 모델이 정의되고 적용되는 경계를 명시적으로 설정한다. 경계 내에서 모델은 일관성을 유지하고, 경계 밖의 이슈에 의해 혼란스러워지지 않는다." — Eric Evans

## 1. Bounded Context란 무엇인가?

DDD에서 가장 중요한 전략적 패턴. "모델이 적용되는 명시적 경계".

### 세 가지 본질

**언어적 경계:** 유비쿼터스 언어가 일관되게 적용되는 범위. 같은 용어가 같은 의미로 사용되는 영역.

**모델 경계:** 도메인 모델이 일관성을 유지하는 범위. 엔티티, VO, Aggregate가 정의되는 영역.

**팀 경계:** 하나의 팀이 소유하고 책임지는 범위. Conway의 법칙이 적용되는 조직적 경계.

> "하나의 팀이 하나의 Bounded Context를 소유해야 한다. 여러 팀이 하나의 컨텍스트를 공유하면 모델의 일관성이 깨진다." — Vaughn Vernon

### 같은 용어, 다른 의미 — 왜 경계가 필요한가

"Account"의 예:
- 인증 Context: 로그인 자격증명, 비밀번호, 2FA
- 뱅킹 Context: 잔액, 거래내역, 이자율
- CRM Context: 고객사, 담당자, 계약
- 소셜 Context: 프로필, 팔로워, 게시물

이 네 가지를 하나의 모델로 통합하면 → God Object. 각 Context에서 독립적 모델로 유지해야 함.

### E-Commerce에서 "Product"의 컨텍스트별 모델

```
카탈로그 Context: Product { name, description, images, category }
재고 Context:     StockItem { sku, quantity, warehouse, reorderPoint }
가격 Context:     PricedProduct { basePrice, discounts, taxes }
배송 Context:     ShippableItem { weight, dimensions, fragile }
```

가장 흔한 실수: "Product"를 하나의 거대한 테이블/클래스로 만드는 것. 시스템 성장 시 수백 개 필드를 가진 괴물이 됨.

## 2. 서브도메인 vs Bounded Context

> "서브도메인은 문제 공간에 존재하고, Bounded Context는 솔루션 공간에 존재한다." — Vaughn Vernon

| | 서브도메인 (Problem Space) | Bounded Context (Solution Space) |
|---|---|---|
| 관점 | 비즈니스 | 기술 |
| 존재 | 소프트웨어와 무관하게 존재 | 소프트웨어 설계의 결과 |
| 정의 주체 | 도메인 전문가 | 개발팀 |
| 질문 | "무엇을 해결해야 하는가?" | "어떻게 해결할 것인가?" |
| 행위 | 발견(Discovery) | 설계(Design) |

### 매핑

- **이상적 (1:1):** 주문 서브도메인 → 주문 Context (그린필드)
- **현실 (N:M):** 레거시, 조직 구조, 외부 시스템으로 인한 복잡한 매핑

> "서브도메인은 발견하는 것이고, Bounded Context는 설계하는 것이다." — Nick Tune (2024)

## 3. 경계 식별하기

경계가 너무 크면 Big Ball of Mud, 너무 작으면 분산 모놀리스.

### 경계를 나타내는 6가지 신호

| 신호 | 설명 | 예시 |
|---|---|---|
| 언어의 변화 | 같은 용어가 다른 의미로 사용 | 영업팀 "고객" vs 지원팀 "고객" |
| 팀/조직 경계 | 다른 팀이 담당하는 영역 | Conway의 법칙 |
| 변경 주기 차이 | 자주 변경 vs 안정적 | 프로모션(주 단위) vs 결제(분기) |
| 비즈니스 역량 | 독립적으로 가치 제공 가능 | "주문을 받을 수 있다" |
| 데이터 소유권 | Source of Truth가 어디인지 | 고객 연락처 → CRM Context |
| 트랜잭션 경계 | 강한 일관성 vs 최종 일관성 | 주문 생성(강한) vs 추천(최종) |

### Event Storming으로 경계 발견

```
1. 도메인 이벤트 나열 (주황색, 과거형)
2. 커맨드와 액터 식별 (파란색)
3. Aggregate 식별 (관련 이벤트 그룹화)
4. Bounded Context 경계 그리기 (언어/모델이 일관된 영역)
```

### 경계 식별 안티패턴

- ❌ **기술적 계층으로 분리** (UI/API/DB Context) — 하나의 기능 변경에 모든 Context 변경
- ❌ **엔티티 단위로 분리** — 너무 세분화, 모든 작업에 Context 간 통신 필요
- ❌ **CRUD 기준으로 분리** — 비즈니스 의미 없음
- ❌ **DB 테이블 기준으로 분리** — 데이터 중심 설계

### 올바른 기준

- ✓ 비즈니스 역량 기준
- ✓ 유비쿼터스 언어 기준
- ✓ 팀 자율성 기준
- ✓ 데이터 일관성 기준

### 적정 크기

5-9명 팀이 소유, 2주 스프린트 내 의미 있는 기능 배포 가능한 크기.

## 4. Context Mapping 패턴 (9가지)

> "Context Map은 프로젝트에 관련된 Bounded Context들과 그들 사이의 관계를 보여주는 문서이다." — Eric Evans

### 협력 관계 패턴

**1. Partnership (파트너십)**
- 두 팀이 공동 목표를 위해 긴밀 협력
- 인터페이스 변경 시 함께 조율
- 적용: 같은 팀이 두 Context 소유하거나, 매우 긴밀한 두 팀

**2. Shared Kernel (공유 커널)**
- 두 Context가 도메인 모델 일부를 공유
- 변경 시 양쪽 합의 필요
- 주의: 공유 범위를 최소화 (범용 VO, 기본 이벤트 인터페이스만)

### 상류/하류 패턴

**3. Customer-Supplier (고객-공급자)**
- 상류(Upstream)가 하류(Downstream)의 요구사항 수용
- 하류가 상류 백로그에 요구사항 추가 가능

**4. Conformist (순응자)**
- 하류가 상류 모델을 그대로 수용
- 상류가 하류 요구를 고려하지 않음
- 적용: 외부 API, 표준 프로토콜, 변경 불가능한 레거시

**5. Anti-Corruption Layer (부패 방지 계층)**
- 하류가 번역 계층으로 자신을 보호
- 외부 모델의 복잡성이 내부로 전파되지 않도록 격리
- 구성: Translator(모델 변환) + Adapter(프로토콜 변환)

**6. Open Host Service (공개 호스트 서비스)**
- 상류가 여러 하류를 위한 표준화된 API 제공
- 적용: 여러 소비자가 있는 서비스, 플랫폼 API

**7. Published Language (공표된 언어)**
- Context 간 통신을 위한 공유 스키마
- 예: JSON Schema, Protocol Buffers, OpenAPI Spec

### 분리 패턴

**8. Separate Ways (각자의 길)**
- 통합 비용 > 이점일 때 의도적으로 통합하지 않음
- 중복 비용 < 통합 복잡도

**9. Big Ball of Mud (진흙 덩어리)**
- 경계 없는 레거시 시스템 (안티패턴)
- 대응: ACL로 격리, 점진적으로 Context 추출

## 5. Context 간 통신 패턴

### 동기 통신 (REST/gRPC)

**장점:** 구현 단순, 즉각 응답, 디버깅 쉬움
**단점:** 시간적 결합, 연쇄 장애, 확장성 제한

### 비동기 통신 (도메인 이벤트)

**장점:** 느슨한 결합, 높은 확장성, 장애 격리, 독립 배포
**단점:** 최종 일관성, 디버깅 복잡, 순서 보장 어려움

### 선택 가이드

| 상황 | 권장 |
|---|---|
| 즉각적인 응답 필요 | 동기 |
| 여러 Context에 알림 | 비동기 |
| 장시간 처리 | 비동기 |
| 단순 데이터 조회 | 동기 |
| 상태 변경 전파 | 비동기 |
| 외부 시스템 연동 | ACL + 비동기 |

> "동기 통신을 기본으로 시작하고, 필요에 따라 비동기로 전환하라." — Sam Newman

### 이벤트 설계 원칙

1. **과거형 명명:** OrderCreated, PaymentCompleted
2. **불변:** 발행 후 수정 불가, 잘못된 이벤트는 보상 이벤트로
3. **자기 완결적:** 처리에 필요한 모든 정보 포함
4. **버전 관리:** 하위 호환성 유지

## 6. Anti-Corruption Layer 심화

> "ACL은 외부 시스템의 모델이 우리 도메인 모델을 오염시키지 않도록 보호하는 번역 계층이다." — Eric Evans

### ACL이 필요한 상황

- 레거시 시스템 통합
- 외부 서드파티 API 연동
- 마이그레이션 중
- 다른 팀의 Context (다른 언어/모델)

### ACL 구조

```
┌─────────────────┐     ┌─────┐     ┌─────────────────┐
│  External System│────→│ ACL │────→│  Our Context    │
│  (복잡한 모델)   │     │(번역)│     │  (깔끔한 모델)   │
└─────────────────┘     └─────┘     └─────────────────┘
```

구성요소:
- **Translator:** 모델 변환 (외부 ↔ 도메인)
- **Adapter:** 프로토콜 변환
- **Facade:** 복잡한 외부 API 단순화
- **복원력 패턴:** Circuit Breaker, Retry, Fallback

### ACL 설계 원칙

1. **도메인 언어 우선** — 공개 인터페이스는 우리 유비쿼터스 언어로
2. **양방향 번역** — 요청/응답/에러 모두 변환
3. **테스트 용이성** — 인터페이스로 추상화, Mock 대체 가능
4. **장애 격리** — 외부 장애가 도메인에 직접 영향 주지 않도록

### ACL 위치 (의존성 역전)

```
domain/
├── PaymentGateway.kt      ← 인터페이스 (도메인 언어)
infrastructure/
├── stripe/
│   ├── StripeAdapter.kt   ← ACL 구현
│   └── StripeTranslator.kt
```

## 7. Bounded Context와 마이크로서비스

| Bounded Context | 마이크로서비스 |
|---|---|
| **논리적** 경계 | **물리적** 경계 |
| 모델의 일관성 범위 | 독립 배포 단위 |
| 모놀리스 내 모듈로 존재 가능 | 프로세스/네트워크 분리 |

**핵심:** Bounded Context ≠ 마이크로서비스. 논리적 경계가 물리적 분리보다 우선.

### 배포 전략

**모듈러 모놀리스 (권장 시작점):**
- 하나의 배포 단위 내에서 Context를 모듈로 분리
- 단순한 운영, 트랜잭션 용이, 리팩토링 쉬움

**마이크로서비스:**
- 각 Context를 독립 서비스로 배포
- 독립 배포, 기술 다양성, 확장성
- 운영 복잡도, 분산 트랜잭션, 네트워크 오버헤드

### 분리 시점

**마이크로서비스로 분리해야 할 때:**
- 독립적 확장 필요
- 다른 기술 스택 필요
- 독립 배포 필요
- 장애 격리 중요

**모놀리스 유지해야 할 때:**
- 경계 불명확
- 팀 규모 작음 (5명 이하)
- 강한 일관성 필요
- 운영 역량 부족

> "모놀리스 우선(Monolith First) 전략을 권장한다. 모놀리스 내에서 모듈 경계를 명확히 한 후, 필요에 따라 마이크로서비스로 추출하라." — Martin Fowler

## 8. 모놀리스에서 Context 분리하기

### 점진적 분리 4단계

```
1. 모듈 경계 식별 → 패키지/네임스페이스로 분리
2. 내부 API 정의 → 직접 참조를 인터페이스 기반으로 전환
3. 데이터베이스 분리 → 공유 테이블을 Context 전용으로
4. 물리적 분리 (선택) → 별도 서비스로 추출
```

### Strangler Fig 패턴

레거시를 점진적으로 새 시스템으로 교체:
1. Facade(API Gateway) 도입
2. 새 Context 추가, 트래픽 점진적 전환
3. 레거시 기능을 하나씩 새 Context로 이전
4. 레거시 제거 완료

## 9. FAQ

**Q: 적절한 크기는?**
5-9명 팀이 소유, 2주 스프린트 내 의미 있는 기능 배포 가능.

**Q: 하나의 팀이 여러 BC를 소유해도 되나?**
가능하지만 경계를 명확히 유지해야 함. 조직 성장 시 팀 분리가 이상적.

**Q: BC와 마이크로서비스는 1:1?**
아니요. 하나의 서비스에 여러 Context 가능 (모듈러 모놀리스).

**Q: Context 간 데이터 공유는?**
직접 공유 안 함. 참조 ID, API 조회, 이벤트 동기화, 최소한의 Shared Kernel.

**Q: 트랜잭션이 여러 Context에 걸칠 때?**
분산 트랜잭션 대신: Saga 패턴, 최종 일관성, 또는 경계 재검토.

**Q: 경계를 잘못 설정했다면?**
리팩토링. 모듈러 모놀리스면 경계 조정 쉬움. 마이크로서비스 분리 후 병합은 매우 어려움.

## 핵심 정리

1. Bounded Context = 언어적 + 모델 + 팀 경계
2. 서브도메인(문제 공간)을 먼저 이해하고, BC(솔루션 공간)를 설계
3. 경계 식별: 언어 변화, 팀 경계, 변경 주기, 비즈니스 역량, 데이터 소유권, 트랜잭션
4. 9가지 Context Mapping 패턴으로 관계 정의
5. ACL로 외부 시스템으로부터 도메인 보호
6. **모놀리스 우선** — 논리적 경계가 물리적 분리보다 먼저
7. 점진적 분리: 모듈 → 내부 API → DB 분리 → 물리적 분리
